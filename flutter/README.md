# Flutter client

One app for iOS, Android and web. The product name, colours, URLs and store
identities come from `brand/brand.yaml` through `scripts/brand-gen.sh` (or
`.ps1`); nothing in `lib/` spells them out. `flutter/lib/brand/brand.dart` is
generated and committed.

## Requirements

- Flutter 3.44.4 (Dart 3.12). `pubspec.yaml` pins the SDK constraint.
- A running API (`scripts/dev-up.sh` from the repo root, or `dotnet run` in
  `backend/`), listening on port 5000 by default.

## First-time setup

```bash
cd flutter
flutter pub get
tool/fetch-fonts.sh          # or: powershell -ExecutionPolicy Bypass -File tool/fetch-fonts.ps1
```

`fetch-fonts` downloads Fraunces, Inter and JetBrains Mono (SIL Open Font
License) from the google/fonts repository into `assets/fonts/` and enables the
`fonts:` block in `pubspec.yaml`. The typefaces are bundled so the web app
never loads anything cross-origin. Until the script has run, the platform
font stands in and everything else works.

## Run

Web, against a local API:

```bash
flutter run -d chrome --dart-define=API_BASE_URL=http://localhost:5000
```

Android emulator (the emulator reaches the host at 10.0.2.2, which is the
default when no define is given):

```bash
flutter run -d emulator-5554
# or, explicitly:
flutter run -d emulator-5554 --dart-define=API_BASE_URL=http://10.0.2.2:5000
```

iOS simulator (localhost is the host machine):

```bash
flutter run -d "iPhone 16"
# or, explicitly:
flutter run -d "iPhone 16" --dart-define=API_BASE_URL=http://localhost:5000
```

A phone on your tailnet has no fixed address at build time. Leave the define
out and type the server address on the setup or sign-in screen (the "Server
address" field, also under You > Server). It is kept in secure storage and
checked with `GET /api/system/version` before anyone signs in.

### Defines

| Define | Meaning |
| --- | --- |
| `API_BASE_URL` | Server origin, without `/api`. `same-origin` means the origin that served the web page (the self-host image builds with this). On mobile `same-origin` counts as unset. Absent: web uses the page origin, Android emulator uses `http://10.0.2.2:5000`, everything else `http://localhost:5000`. |
| `APP_VERSION` | Build name compared with the server's `minClientVersion`. `dev` (default) never blocks. |
| `MIN_SERVER_VERSION` | Oldest server this build accepts. Default `0.1.0`. |

## Build

```bash
flutter build web --release --dart-define=API_BASE_URL=same-origin --no-web-resources-cdn
flutter build apk --release --dart-define=APP_VERSION=0.1.0
flutter build ipa --release --dart-define=APP_VERSION=0.1.0
```

`--no-web-resources-cdn` keeps the CanvasKit runtime in the build output
instead of loading it from gstatic.com, which the no-cross-origin promise
requires for the self-hosted web app.

## Verify

```bash
dart format .
flutter analyze
flutter test
dart run build_runner build --delete-conflicting-outputs   # after editing lib/offline/outbox_database.dart
```

`lib/offline/outbox_database.g.dart` is generated by drift and committed, so a
clean checkout builds without running build_runner. Regenerate it whenever the
tables change.

## Health data collection (Package 2)

Phones collect; the server stores. The flow on a phone is:

1. **Collector** (`lib/collectors/`): one Dart interface, `HealthCollector`,
   with a platform implementation behind the `app.selfkept/health` method
   channel and the `app.selfkept/health/changes` event channel. iOS reads
   HealthKit (`ios/Runner/Health/HealthKitCollector.swift`), Android reads
   Health Connect (`android/.../health/HealthConnectCollector.kt`). Web and
   desktop get `NoopHealthCollector`, which reports "not available", and the
   Sources screen says that collection happens in the phone apps.
2. **Outbox** (`lib/offline/`): every collected row is written to a local
   SQLite database (drift) before anything is sent. `SyncEngine` flushes it to
   `POST /api/ingest/batch` in pages of up to 2,000 rows, deletes rows only on
   a 200, and keeps them on any failure. On web the outbox is an in-memory
   stub, since web never collects.
3. **Cursor**: the collector returns an opaque resume token with every page
   (HealthKit anchors, Health Connect changes tokens, both as JSON). Dart keeps
   it locally (in the outbox's `sync_state` table) and the engine mirrors it to
   the server source with each accepted batch, so a reinstalled app resumes
   from where the last install stopped. A page that leaves rows behind repeats
   the previous cursor rather than advancing it, so the server never records a
   position ahead of what it holds.
4. **Providers**: `SourcesProvider` (the server's list of sources),
   `CollectorProvider` (the connect and collect state machine) and `SyncEngine`
   (a `ChangeNotifier`) are wired in `main.dart`. The collector runs a pass on
   app start (after sign-in), on every foreground resume, when the platform
   reports a change, and when you tap "Sync now".

### Backfill

The first connect reads the last 90 days. It is paged: each
`collectSince` call returns at most 1,500 rows and says whether more are
waiting; the provider queues and flushes each page before asking for the next,
so a first sync on a busy watch is many small requests rather than one large
one and can stop and resume without losing its place. The backfill window is
always passed to the collector; types that already have a cursor ignore it,
types without one (a new type, a reinstall) use it.

### Permissions

**iOS** (`ios/Runner/Info.plist`, `ios/Runner/Runner.entitlements`):

- `NSHealthShareUsageDescription` and `NSHealthUpdateUsageDescription` (the
  second is required by App Review even though the app only reads).
- Entitlements `com.apple.developer.healthkit` and
  `com.apple.developer.healthkit.background-delivery`. The HealthKit capability
  must also be enabled on the App ID in the developer portal.
- `UIBackgroundModes: fetch`, so iOS may wake the app for a delta pass between
  HealthKit deliveries.
- HealthKit never says whether read access was granted; a denied type just
  returns nothing. The app treats a completed prompt as granted.

**Android** (`android/app/src/main/AndroidManifest.xml`):

- One `android.permission.health.READ_*` per record type in the contract, plus
  `READ_HEALTH_DATA_IN_BACKGROUND` and `READ_HEALTH_DATA_HISTORY`.
- The permissions rationale activity (`HealthPermissionsRationaleActivity`)
  with the `ACTION_SHOW_PERMISSIONS_RATIONALE` intent filter and the
  `ViewPermissionUsageActivity` alias Android 14 requires.
- `<queries>` for the Health Connect package, and `minSdk = 28`.
- Health Connect limits history reads to 30 days unless
  `READ_HEALTH_DATA_HISTORY` is granted; the 90-day backfill needs it.

### Android background approach

`HealthSyncWorker` is a WorkManager periodic job every 15 minutes (the
platform minimum) with a network and battery-not-low constraint. It runs
without a Flutter engine: it reads Health Connect with the same `HealthReader`
the foreground uses, maps records to contract rows, writes them as a JSON file
under `files/health_pending/`, and posts on `HealthChangeBus`. The next
`collectSince` call drains those files into its result before reading the live
delta, so the rows go through the normal outbox and sync engine. If the app
process is alive when the worker finishes, the bus delivers a change event and
the open app syncs at once; otherwise the rows wait for the next launch or
resume.

This was chosen over a headless Flutter engine because a second engine means a
second isolate that owns the outbox and the sync engine, a Dart callback
dispatcher to register, and a cold engine start every 15 minutes. The file
hand-off keeps one owner of the outbox and a worker that finishes in well
under a second. The cost is that the send, not the read, waits for the app to
be opened.

Health Connect changes tokens are kept natively (SharedPreferences
`health_connect_tokens`) because the worker needs them without Dart; the
cursor Dart stores on the server is the same map, and a reinstalled app seeds
the native store from it.

### Testing the collectors on a device

Neither collector can be exercised on this machine (the iOS code needs Xcode;
the Android code needs a phone or emulator with Health Connect). To test:

**iOS**: open `ios/Runner.xcworkspace`, make sure the HealthKit capability is
enabled on the signing team's App ID, then `flutter run` on a physical iPhone
(the simulator has HealthKit but no data of its own; add some in the Health
app on the simulator). Go to You > Sources, tap "Connect Apple Health",
allow the categories, and watch the progress line. Background delivery can be
checked by locking the phone, recording a workout on a watch, and looking at
the source's "Last sync" an hour later.

**Android**: an emulator with Google Play (API 34 or higher has Health Connect
built in; on API 33 install it from Play) and the Health Connect toolbox app
to insert sample data. `flutter run`, You > Sources, "Connect Health Connect",
allow the categories plus background and history access. To run the worker on
demand without waiting 15 minutes:

```bash
adb shell am broadcast -a "androidx.work.diagnostics.REQUEST_DIAGNOSTICS" -p app.selfkept.android
adb shell cmd jobscheduler run -f app.selfkept.android <job id from logcat>
```

Then open the app: the Sources card on Today shows the rows waiting and the
sync engine sends them.

**Without a device**: `test/providers/collector_provider_test.dart` drives the
whole state machine with `FakeHealthCollector`, and
`test/offline/sync_engine_test.dart` covers flush, failure and cursor handling
against `FakeApiClient`.

## Today, Trends, Insights (Package 3)

The server decides what is notable; the client only shows it against the
person's own baseline. Three providers, one service each, all on the
abstract `ApiClient`:

- **Today** (`TodayProvider`, `GET /api/today`): the day's sentence is the
  hero, set in the display serif; beneath it three readiness chips (Sleep,
  HRV, Resting HR) say "in your range", "below your range" or "above your
  range" with a sage, amber or neutral dot (never red: amber marks only the
  side worth watching, so a long night or a high HRV stays sage); then at
  most two `InsightCard`s, the check-in entry and the Sources card. When the
  server says `learning`, a quiet "Still learning your normal." sits under
  the sentence. Pull to refresh. A kept check-in bumps
  `CheckinsProvider.keptCount`, which Today watches and reloads on.
- **InsightCard** (`lib/widgets/insight_card.dart`): severity label and a
  2 px left rule in sage (notice), amber (watch) or terracotta (clinician),
  the text at reading size, metric chips, and "Helpful", "Knew that",
  "Not right" plus dismiss. Reactions and dismissals go through
  `InsightsProvider` only; it keeps every card it has touched in a `known`
  map, and Today reads its cards through that map, so both screens agree
  the instant a reaction is tapped and roll back together if the server
  refuses. New cards fade in over `Motion.standard`.
- **Trends** (`TrendsProvider`, `GET /api/trends`, `GET /api/trends/{metric}`):
  a horizontal chip picker sorted by product priority (sleep, HRV, resting
  HR, temperature, SpO2, respiratory rate, steps, exercise, energy, weight,
  mood, Oura scores), a 28 or 90 day toggle, and `TrendChart`, a
  `CustomPainter` with the p25 to p75 band as a sage fill, median28 as a
  hairline, the daily line and points in the primary colour, outliers past
  p10 or p90 ringed in amber, week ticks and three to five tabular y labels.
  Tapping (or dragging across) a point writes the day, value and low/high in
  the caption beneath the chart; nothing floats. Sleep minutes read as
  "7 h 40" everywhere (`lib/utils/metric_format.dart`). Series are cached per
  metric and window for the session.
- **Insights** (`InsightsProvider`, `GET /api/insights`): the last 90 days
  grouped by day, newest first, with severity chips and an "Include
  dismissed" toggle (the toggle refetches; severity filters locally).
- **You > Server** gains "Recompute insights" (`POST /api/insights/recompute`,
  confirmed with a toast) and shows the server's feature list as chips, so
  `insights.model` is visible when a local model is phrasing sentences.

## Labs (Package 4)

A monthly panel is added by photo, by screenshot or by typing. Nothing is
stored until the person has checked every value.

- **Scan flow** (`lib/pages/lab_entry_page.dart`, route `/labs/add`): on a
  phone, "Take a photo" or "Choose a screenshot" (`image_picker`), then the
  text is read on the device, the lines are sent to `POST /api/labs/parse`
  (the matching rules live on the server), and the review sheet opens
  prefilled. The sheet has a collected-on date, a provider, and one row per
  marker that applies to the person (ratios are computed by the server and
  are not rows). Rows the parser was unsure about (confidence under 0.7) get
  an amber border and "Check this one". "Keep these results" posts the report
  with the image in one call (`POST /api/labs/reports`).
- **OCR is on-device**: `google_mlkit_text_recognition` (ML Kit, Latin
  script) runs on a temporary copy of the image on Android and iOS, with no
  network. The image and the values reach the person's own server only when
  they keep the results. The scanner sits behind `TextScanner`
  (`lib/services/ocr/ocr.dart`, conditional import) so a web build never
  compiles `dart:io`.
- **Web is type-in only**: there is no on-device recognition in a browser, so
  the same review sheet opens empty. Desktop builds behave the same way.
- **Labs tab** (`lib/pages/labs_page.dart`): one tile per marker in panel
  order, grouped (Hormones, Thyroid, Heart, Metabolic, Blood count, Kidney,
  Liver), with the last values as a sparkline over the usual range band.
  Out of range is amber ("Above range", "Below range"); the clinician tier is
  terracotta with "Worth raising with a clinician". Never red. Tap a tile for
  the marker page (`/labs/marker/:key`): ranges in words, what it is, what
  moves it, history and where the range comes from. Panels can be deleted.
- **Clinician summary**: the button on Labs and Insights fetches
  `GET /api/labs/summary.pdf` for the last 90 days. On web it opens in a new
  tab; on a phone it goes to the share sheet (`share_plus`).
- **Permissions**: iOS asks for the camera ("To read the results from a photo
  of your blood test.") and the photo library ("To read the results from a
  screenshot of your blood test."), both in `ios/Runner/Info.plist`. ML Kit
  needs iOS 15.5 or later, so `IPHONEOS_DEPLOYMENT_TARGET` is 15.5; if you
  generate a Podfile, its `platform :ios` line must be `'15.5'` too. Android
  needs no manifest entry: the system photo picker and the camera intent
  handle access, and `minSdk` is already 28.

## Assistants and Oura (Package 5)

- **Assistants page** (`lib/pages/connections_page.dart`, route
  `/connections`, reached from You, then Assistants, then Manage): the MCP
  address with a Copy button and the Open WebUI setup line; the assistants
  that are connected, each with Disconnect; access tokens; and what
  assistants have been asked to remember, each with a Forget button. It reads
  `GET /api/connect` and `GET /api/connect/memory`. Every removal asks first.
- **Consent page** (`lib/pages/consent_page.dart`, route
  `/connect?request=<id>`): where an assistant sends a person to say yes or
  no. It shows who is asking, where it will return to, what it may read and
  who the person is signed in as. Allow and Deny post to
  `POST /api/oauth/request/{id}/decision`, then the browser goes to the
  returned address: the same tab on web, the system browser on a phone (the
  app then returns to the Assistants page). A missing, expired or already
  answered request shows one calm message. The page takes an injectable
  opener so tests capture the address.
- **Sign-in round trip**: a signed-out person who opens `/connect?...` is sent
  to `/login?from=<encoded location>` and returned there after signing in.
  `resolveRedirect` takes the full `location`; the mechanism is generic, but
  only `/connect` (`returnPaths`) starts it. Only an in-app `from` that starts
  with a single slash is honoured (`safeReturnPath`). The place to return to
  also rides through `/splash?from=...` while the app starts.
- **Access tokens**: "Create token" asks for a name and whether the token may
  remember notes. The secret is shown once, in its own dialog with a Copy
  button, and is never listed again; the list shows the prefix, the scope in
  words ("Can remember notes" or "Read only"), when it was made and last
  used. Revoke asks first.
- **Oura card** (`lib/pages/sources_page.dart`, below the phone collector):
  not configured on the server shows the setup sentence and no button; not
  connected shows "Connect Oura", which opens Oura in the same tab on web and
  returns to `/sources?oura=connected` (or `oura=error`, which shows a
  message); connected shows when it was connected, the last pull, the number
  of readings, the last error in amber, "Pull now" (the status reloads two
  seconds later) and Disconnect. Readings already brought in stay.
- Data comes from `ConnectService` and `OuraService`, held by
  `ConnectProvider` and `OuraProvider`; both clear on sign-out.

## Layout

```
lib/
  brand/        generated Brand constants (do not edit)
  collectors/   HealthCollector interface, channel implementation, no-op
  config/       AppConfig: defines and platform defaults
  models/       DTOs with fromJson tolerant of camelCase and PascalCase, enums
  offline/      drift outbox (tables, generated code, repository), SyncEngine
  pages/        authenticated pages; pages/public/ for splash, setup, login, join
  providers/    ChangeNotifiers: auth, startup, server settings, profile,
                household, sources, collector, check-ins
  router/       go_router with the redirect guard (resolveRedirect is pure)
  services/     Dio ApiClient, token store, endpoint services, version handshake
  theme/        tokens and the light and dark ThemeData
  utils/        JsonReader, ApiException, relativeTime
  widgets/      shared surfaces: cards, page body, check-in entry, banner
test/           mirrors lib/; helpers/ has the FakeApiClient, FakeHealthCollector
                and TestHarness
tool/           fetch-fonts scripts
ios/Runner/Health/        HealthKitCollector.swift
android/.../health/       HealthConnectCollector.kt, HealthSyncWorker.kt,
                          HealthPermissionsRationaleActivity.kt
```

## Conventions

- Provider + ChangeNotifier only. Dio with `queryParameters:`. go_router.
- No `dart:io` in code that can run on web. Platform checks use
  `package:flutter/foundation.dart`.
- Tokens live in `flutter_secure_storage` on mobile. On web the access token
  is memory-only and the refresh token is an HttpOnly cookie.
- Every enum has `fromInt`, `fromString`, `displayName` and `toJson`.
- No red for health states: amber is attention, terracotta is the clinician
  tier. Cards are 20 px radius with a hairline border and no shadow.
- No em dashes in code, comments, copy or docs.
